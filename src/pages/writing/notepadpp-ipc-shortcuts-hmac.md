During our Notepad++ research, we independently found that ordinary local code could reproduce the HMAC used to validate `shortcuts.xml`. The key was a readable machine identifier, so a matching integrity value did not establish that the user had approved the command file.

We later learned that **Nguyen Van Hiep of Lo Security Labs had submitted the issue earlier**. Notepad++ had already published his report as **GHSA-grw6-cw7j-3qfg** on August 24, 2026. Our work was an independent rediscovery; first-report credit belongs to Hiep. [Earlier published advisory](https://github.com/notepad-plus-plus/notepad-plus-plus/security/advisories/GHSA-grw6-cw7j-3qfg).

The earlier report connects the readable HMAC key to an external `WM_COMMAND` trigger in **8.9.7**, forming an elevation chain. Our retained experiments concern **8.9.8**, where the message-trigger behavior differed. This article explains how we reached the same key-management finding and how it fits the already published chain, keeping the two versions' evidence separate.

## How we reached the same finding

We traced the command-validation code to the HMAC helper, which read `MachineGuid` from the Windows registry. We then checked whether an ordinary local process could obtain the same value and reproduce the application's calculation. In the August 29 test, our offline HMAC matched the value generated by Notepad++ over identical command-file bytes.

That baseline answered a specific question: the application's key and computation were reproducible outside its approval workflow. The baseline had used the application's validation action, so matching its digest alone was not proof of a newly forged approval or of an end-to-end elevation chain.

Our initial duplicate search missed Hiep's advisory. The August 31 correction identified the overlap and withdrew the claim that the readable-key root cause was new. Independent discovery describes how we found it; it does not change who reported it first.

## Two decisions that needed separate protection

The Run menu supports saved commands. Their executable content lives in `shortcuts.xml`; the expected integrity value lives in `config.xml`. Before executing a saved command, the implementation compared the calculated and stored HMAC values. A mismatch stopped execution with a warning. The public report includes the relevant excerpt and references the [8.9.7 command implementation](https://github.com/notepad-plus-plus/notepad-plus-plus/blob/v8.9.7/PowerEditor/src/NppCommands.cpp).

There are two separate security questions:

- Is this the command content that a trusted user approved?
- Is this execution request coming from an authorized context?

Answering only one is insufficient. Approved content should not become an unattended privileged operation merely because another process can select its command identifier. Conversely, a legitimate invocation should not give untrusted configuration the appearance of prior approval.

That is why this case belongs in one chain. The configuration step prepared an accepted command; the message step activated it.

## Why the HMAC did not establish approval

Our source review identified `MachineGuid`, read from `HKLM\SOFTWARE\Microsoft\Cryptography`, as the HMAC-SHA256 key. The same user could also write the command file and stored comparison value. This matched the root cause already described in Hiep's report: local code could recreate the integrity value for changed content. [HMAC findings in the earlier advisory](https://github.com/notepad-plus-plus/notepad-plus-plus/security/advisories/GHSA-grw6-cw7j-3qfg).

The conceptual relationship is:

```text
command file + authentication key → integrity value
stored integrity value == calculated value → command gate accepts
```

HMAC authenticates data against parties who do not possess its key. A machine identifier can be stable and machine-specific without being secret. Placing a value in the machine registry does not imply ordinary processes lack read permission.

If the same actor can change the data, obtain the key, and replace the expected result, matching digests establish internal consistency. They do not establish who approved the content. No weakness in SHA-256 is needed.

Access to one's own configuration is also not permission to act through an elevated process. A security boundary can exist between two processes belonging to the same Windows user.

## Turning a request into execution

Windows applications commonly receive `WM_COMMAND` notifications for menu actions. A handler maps an identifier to an operation; that identifier does not prove a human selected a menu item. In the reported path, passing the HMAC comparison led to the saved command's execution routine.

Transport rules matter before the handler is reached. Microsoft documents that `SendMessageW` is subject to User Interface Privilege Isolation, or UIPI, and that a UIPI-blocked send produces access-denied error 5. Application message handling cannot safely be inferred from a message number alone. [SendMessageW documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendmessagew).

Windows also provides per-window and process-wide filters, and some messages receive special treatment. Thus “every message below `WM_USER` crosses every integrity boundary” is an unsafe generalization. The source process, target window, filter configuration, and command path must be considered together. [ChangeWindowMessageFilterEx documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-changewindowmessagefilterex).

The earlier advisory reports the resulting Medium-to-High chain. Its displayed message-delivery experiment uses Low-to-Medium processes. Those observations belong to the earlier report; our rediscovery of the key weakness does not amount to independently reproducing its complete 8.9.7 chain or every Windows integrity transition.

## Preconditions make the chain understandable

At a high level, the published scenario connects these states:

```text
same-user local attacker
    → prepared command configuration and matching integrity state
    → elevated editor loads that state
    → external request reaches its command handler
    → operation runs with the editor's elevated permissions
```

This is a local scenario, not a remotely delivered document exploit. It depends on an elevated editor consuming configuration the less privileged process can influence. Editing a file that an existing instance never reloads does not demonstrate that the prepared command entered its in-memory menu.

The advisory's “zero-click” wording concerns activation after the elevated instance is available. It does not mean the attacker creates administrator privileges without an elevated target or bypasses the user's initial elevation decision. Its CVSS metadata explicitly records user interaction as required.

## Published status and the boundary of this account

The project labels the advisory **High, CVSS 3.1 8.2**, with `AV:L/AC:L/PR:L/UI:R/S:C/C:H/I:H/A:H`. It lists **8.9.7** as affected, **None** under patched versions, and no known CVE. These are the published fields, not a new severity assessment. [Advisory status](https://github.com/notepad-plus-plus/notepad-plus-plus/security/advisories/GHSA-grw6-cw7j-3qfg).

Our archived local check against 8.9.8 recorded the Medium-to-High `WM_COMMAND` attempt being refused with `ERROR_ACCESS_DENIED`. That narrow negative result does not show this whole chain still worked in 8.9.8. Nor does it supply a vendor-confirmed fixed-version field that the advisory does not provide.

The broader lesson is to protect both authority over executable configuration and authority to invoke it. A digest comparison and a GUI message each have a precise job. Their combination becomes an authorization boundary only when the key, stored approval, loaded content, and execution request all receive appropriate protection.
